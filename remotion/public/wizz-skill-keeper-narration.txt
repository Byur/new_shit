Wizz Skill Keeper｜设计纪实与实践教程

00 开篇
当 Agent 通过 Skill 读取文件、访问站点、调用账号与付费服务，风险不再只藏在代码里。
提示词怎样施压、费用何时披露、权限怎样被解释，同样会改变用户的决定。
这是一段把真实安全审查，变成可复用 Skill 守门方法的故事。

01 问题从哪里来
故事从一个内容创作 Skill 开始：注册、积分、趋势查询与违禁词检测被绑在同一条工作流里。
静态检查发现了内容外发、账号密钥读取、URL 抓取和营销引导，但单个敏感词仍不足以下结论。
文档说会上传原始文案，代码却只发送来源字段。审查必须同时看声明、代码、调用点与数据流。
第一条教程原则因此出现：风险判断不是匹配关键词，而是把证据连接成一条可验证的路径。

02 第一阶段做什么
第一阶段没有追求包办一切，而是主动把范围做窄：本地、只读、静态、可追溯。
默认报告先讲影响与行动；路径、源码、域名和凭据名留在独立证据文件中。
运行时沙箱、网络拦截和自动处置暂不进入第一阶段，因为它们会改变权限与威胁模型。
第二条教程原则：好用的 MVP 不是什么都做，而是把最关键的判断链做完整。

03 谁负责判断
最重要的转向，是承认扫描器没有资格给出最终答案。
扫描器擅长找文件、调用点、提示词片段和候选关系；它不擅长理解意图、语境与真实影响。
Agent 必须逐条复核证据，区分能力、影响与意图，再生成风险等级、建议和关系图。
正式报告还要求证据 ID 完整覆盖：缺失、多余或关系未复核，流程就不能越过门槛。

04 风险规则如何收紧
规则不是越多越安全。真正困难的是定义：什么证据足以让系统说重话。
本地读取若只服务声明功能，不外发、不进入不可信执行链，就只记录能力，不计风险。
商业诱导可以独立升高严重度；但高风险仍不自动等于隔离，处置必须看现实伤害路径。
执行任意代码必须证明不可信输入能到达宿主执行入口。固定打开本地报告，不属于任意代码执行。
内容进入 HTML 先叫渲染边界；只有能推导出突破方式、触发路径与缺失防护，才能称为不安全。

05 真实审查如何反校准
真实目录让理论规则接受反向校准。一个地图 Skill 最初被判成高风险和任意代码执行。
重新取证发现，它只是用固定参数打开自己生成的 HTML；没有不可信输入控制宿主命令。
任意执行标签被撤销，渲染问题降为中性的内容边界，整体风险也随证据回落。
另一项 Skill 因账号密钥传输、关闭 TLS 校验与反复商业引导，仍有独立证据支撑较高风险。

06 页面如何被磨出来
HTML 不是报告外壳。它是防止技术结论再次误导普通用户的最后一层。
扫描卡片只保留总览，详细分析进入抽屉；风险标签按数据、执行、提示和费用分组。
关系图常驻，但只能显示 Agent 核验后的边；没有关系，也应成为用户能感知的结论。
交互用克制的 2 像素圆角、8 像素节奏、低饱和强调色和明确的复核引导，减少恐慌与歧义。

07 定位、传播与验证
最终定位不是替用户判断一切的安全裁判，而是在使用前帮助用户看清边界的 Skill 守门人。
传播先讲必要性：文件、账号、外部站点与付费操作已经进入 Agent 的日常工作流。
营销不靠恐惧。未知不等于危险，能力信号也不等于恶意；每句重话都要有证据支撑。
验证也从扫得快转向证据是否被完整理解。先看清，再安心使用。

08 结语
这套方法最后形成了一条清楚的责任链。
本地工具负责收集事实，Agent 负责理解语境，界面负责解释结论。
处置权仍留给用户。它守住的不只是 Skill 的安全，也是用户对 Agent 结论的信任。
