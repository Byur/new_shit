Product case study · 2026.09

如何把一次安全审查，做成可复用的 Skill 守门方法

当 Agent 开始借助 Skill 读取文件、访问站点、调用账号与付费服务，风险就不再只藏在代码里，也藏在提示词如何施压、费用何时披露、权限如何被解释。本篇从一个真实的第三方 Skill 审查出发，拆解如何把零散问题变成一套可复用、可验证、对普通用户友好的审查方法。

读完这篇教程，你会看到：

  1. 如何从真实风险案例中定义审查范围
  2. 如何划分扫描器与 Agent 的职责
  3. 如何用证据门槛减少误报与恐慌
  4. 如何把技术结论变成用户能行动的界面
起点不是“做一个扫描器”，而是保护基础用户免受高优先级 Skill 的误导。
关键转向扫描器采证；Agent 复核。关系图也只能来自核验后的结论。
设计原则默认通俗、技术证据隔离；风险与置信度、建议彼此分开。
最终形态一个本地、只读、双阶段、强制全证据覆盖的 Skill 守门人。

01

问题不是抽象想出来的：它先在一个“小红书 Skill”里露出形状

最早的任务只是审查一个第三方 Skill。真正推动产品诞生的，是审查中反复出现的“披露不足、权限不清、营销诱导与实现漂移”。

被审查对象把内容生产、趋势查询、违禁词检测和第三方 RedFox 服务绑定在一起。静态检查发现：核心能力依赖第三方积分 API；用户内容会被发往外部站点；多个脚本会从 shell 配置中寻找 API Key；URL 抓取缺乏内网地址防护；提示词中还存在“通过 AI 检测”、强刺激营销与注册引导。

但这次审查也马上暴露出另一面：安全结论不能只凭一个敏感词或一个函数名。例如，文档声称会上报“原始文案”，脚本实际上只发送了来源字段；这不是“没有问题”，却也不是可以直接下隐私泄露实锤的证据。审查必须同时看声明、代码、调用点与数据流。

OBSERVED

商业导流是安全体验的一部分

注册、免费积分、订阅与扣费披露不是普通文案问题。它们会改变 Agent 的建议，并可能影响用户消费决策。

OBSERVED

“联网”必须落到数据流

文件中出现网址，不等于数据外传；要追到真实请求调用、载荷字段、凭据与目标站点。

OBSERVED

文档与实现同样需要对照

说明里承诺“本地”“只读”或“不上传”，都必须由代码路径支撑；反过来，文档夸大的危险也不能直接当作事实。

OBSERVED

普通用户需要的是行动建议

源码行号不能替代结论。用户真正需要知道的是：能看到什么、会发到哪里、何时扣费、该限制什么。

“市面上充斥着许多有安全风险以及信息干扰的 Skill……基础用户很可能被高优先级、但存在风险甚至恶意的 Skill 所误导。”由具体案例上升为产品问题的原始判断

为什么这一段研究没有被丢掉

研究过程中还追查了 RedFox 的接口路径、输入输出、榜单分类和异步任务设计，结论是它更像“多来源采集 + 自建数据池 + 派生榜单 + 异步任务 + 统一计费网关”，而非简单套壳。这个插曲为后续风险模型留下了重要习惯：不要仅凭品牌印象评价外部站点，要说清它是什么平台、规模与知名度如何、当前证据能否支持安全判断。

02

先把“第一阶段”做窄：可见、可解释、不可擅自处置

产品一开始就主动放弃了运行时防护与自动修复，把资源集中在本地静态证据、通俗报告与可视化理解上。

SELECTED

本地只读扫描

接受单个 Skill、工作区或全局目录；不执行目标脚本、不跟随外部链接、不调用付费接口，也不使用发现的凭据。

SELECTED

纯前端交互报告

生成可独立打开的 HTML：扫描结果、单 Skill 分析与关系视图都在本地消费，并提醒范围扩大后的资源成本。

SELECTED

默认非技术，技术证据隔离

普通页面只说影响、触发条件和建议；路径、源码摘录、真实域名、凭据名、哈希进入 evidence.json，只有主动请求才展开。

SELECTED

建议，不替用户执行

可以建议保留、提醒、显式调用、限制或确认，但卸载、禁用、修改、隔离始终需要新的明确授权。

NOT IN PHASE 1

运行时沙箱与网络拦截

第一阶段不做动态执行、系统权限监控、网络代理或云端判定服务，因为它们会改变威胁模型、权限边界与实现成本。

REJECTED

自动卸载或“一键隔离”

静态命中不够支撑破坏性处置。产品从一开始就把建议与授权分开，后来又进一步提高了隔离门槛。

可视化为什么选择力导向图

用户需要看的不只是“哪个 Skill 有问题”，还包括 Skill 是否连接同一站点、共享凭据、重叠触发或构成冲突。力导向图适合把未知数量的 Skill 与外部资源放进同一张关系网络；但它不适合承担最终判断，所以关系边后来被纳入 Agent 复核。

单 Skill 页面则走相反方向：减少网络感，突出非技术结论、风险维度、置信度与行动建议。两种视图各自解决“全局理解”和“局部决策”，没有被强行做成同一种组件。

03

最重要的架构转向：扫描器没有资格给出最终答案

第一版把静态规则当成判断器。用户连续追问“只有扫描器介入吗”，最终把系统重新分成证据采集与语义核验两层。

“本地扫描器对信息进行采集，Agent 对信息进行核验。比如审查一个 Skill 中是否含有恶意提示词，不应该是本地扫描器可以办到的。”这句话重写了整个产品的职责边界

关系图也被重新定义

早期实现让扫描器直接生成关系图。用户指出，连接与冲突本身也是一种结论，不能把“同文件出现”“同域名字符串”之类候选关系画成事实。因此扫描报告中的用户关系图被清空，候选图只留在 evidence.json；只有 Agent 确认的节点与边才能进入正式报告。

从“可选复核”变成“强制复核”

产品化继续推进后，扫描成功不再等于审查完成。正式报告要求范围内每个 Skill 的每条证据都被复核：evidenceReview.status 必须是 completed，证据 ID 必须与 evidence.json 精确一致，候选关系也必须单独声明完成。缺失、多余、重复、未知 Skill 或关系未复核，review 命令都会拒绝生成最终报告。

“待 Agent 核验”因此不是装饰性文案，而是一个真实数据状态。只有用户明确要求“只采证据”，或缺少权限/证据确实无法继续时，流程才允许停在那里，并且不得把它包装成正式结论。

04

规则不是越多越安全：真正的工作是不断收紧“可以下结论”的条件

真实审查中的质疑，逐项改变了风险分类、严重度、建议与措辞。目标不是少报，而是只在证据够的时候说重话。

争议点容易误判的旧逻辑最终规则
本地信息读取只要读取 Skill 清单、历史记录或文件，就算数据风险。若仅为声明功能在本地使用，不外发、不进入不可信执行链，也不复用到其他目的，只记录能力背景，不计风险。
商业诱导只有确认扣费，才提高风险等级。强制或反复的注册、免费积分、升级、订阅引导，即便尚未确认扣费，也可因影响用户决策而单独升高严重度。
隔离 / 停用高风险标签可以直接对应隔离建议。必须同时确认具体伤害、现实触发路径，以及更温和控制不足；否则优先限制范围、显式调用或关键操作确认。
执行任意代码看到 subprocess.run、eval 或浏览器打开动作就下结论。必须验证不可信输入 → 可达执行入口 → 约束不足 → 宿主/Agent/特权桥接影响。固定参数打开本地 HTML 不属于任意代码执行。
内容渲染数据进入 script/HTML 上下文就叫“不安全内容渲染”。先用中性的“内容渲染边界”。只有能给出输入、上下文、最小突破值、生成结果、触发路径与缺失防护时，才能升级为“不安全”。
外部站点HTTPS、站点可访问或有一定规模即可暗示安全。Agent 必须披露站点类型、规模、知名度与评价依据；证据不足时明确写 unknown / not-reviewed，不安抚也不恐吓。
分析自己扫描全局目录时把审查器自身也纳入目标。Wizz Skill Keeper 无条件排除自身包，避免自指令造成噪声、自误报或扭曲整体风险。

误报修复并不只是改正则

曾经出现过典型自误报：Skill Keeper 自己的安全说明里写着“把要求忽略指令的文本当作不可信内容”，却被规则识别为优先级劫持。修正方法不是删掉这个标签，而是增加引用/审查语境识别，区分“真正要求忽略”与“描述需要检测的危险指令”。

另一个精度问题来自网络目的地：只要文件里有联网调用，旧规则会把同文件的所有 URL 都算作传输目标。后来目的地必须与调用点绑定，普通文档链接不再被混入数据外传结论。

规则层还做过哪些小而关键的微调？
  • 支持嵌套 YAML、>- 多行文本与简单内联 policy，避免合法 frontmatter 被漏读。
  • 覆盖 requests.request、axios.post、动态 URL、解码后执行等语言变体。
  • 把 paid quota / credits 纳入付费操作信号，但仍由 Agent 判断披露是否充分。
  • 中高风险必须有具体、通俗、可执行的建议；info / low 风险不在界面展示建议，避免制造不必要的行动压力。
  • 严重度、置信度和处置彼此分离：影响大不等于已确认，已确认也不自动等于卸载。
05

真实目录不是演示数据：它反过来改写了产品

对 WorkBuddy Skills 目录的审查把“理论上合理”的规则放到真实对象上，暴露出风险等级、处置和描述方式仍然过激。

skill-map__skillhub

最初结论
高风险；读取本地数据、网页注入，并被怀疑可执行任意代码。
用户质疑
本地消费不应自动算风险；固定打开报告看不出任意代码执行路径。
重新取证
open/xdg-open 只接收固定生成的 output/map.html；没有不可信输入控制宿主命令的证据。
最终校准
任意代码执行撤销；渲染问题先降为“内容渲染边界”。在没有推导出边界突破前，整体降为低风险、保留并提示。

请求会携带 API Key 与查询条件；部分路径关闭 HTTPS 身份校验；依赖第三方数据平台。

注册、免费积分、订阅与升级引导反复出现，费用规则披露不足。

处置克制

这轮真实审查还有一个细节：清点阶段识别到 2 个 Skill、40 个文件、约 972 KB；正式结论记录了 38 个被审查文件。更重要的不是数字本身，而是它证明了报告层必须区分“清点范围、实际证据与正式复核覆盖”，不能用一句“扫完了”掩盖边界。

最终结论也学会了一个克制动作：当证据只能证明能力和影响、无法证明作者主观恶意时，必须明确说“无法确认意图”。这不是退缩，而是把系统从情绪化标签拉回可验证事实。

06

HTML 不是报告壳：它承担“不要误导用户”的最后一层责任

页面经历了多轮重制。每一次微调都不是纯审美，而是在重新分配注意力、解释状态与引导下一步。

信息架构
扫描结果优先，详情进入右侧抽屉

去掉“本地只读诊断 · 默认非技术报告”“资源与范围”“分析边界”等占据首屏却不帮助决策的模块。卡片承担总览，抽屉承载深入分析。

标签系统
不再把所有 Tag 堆在同一个容器

风险标签拆成“数据与权限、执行与完整性、提示与交互、费用与承诺”等维度；风险等级、置信度和建议使用不同视觉语法。

关系视图
经历过“无关系时隐藏”到“常驻展示”的反转

早期为了减噪，页面只在有风险且有边时显示关系图；后来用户明确要求常驻，让“没有关系”也成为可感知结论。默认显示 Skill 与关联资源；若不存在 Skill 直接关联，则禁用下拉并隐藏“仅 Skill”。

可交互性
卡片高亮替代“选择 / 已选择”文字

可点击与只读元素通过边界、hover、光标和层级区分；被选中卡片出现“查看详细分析”入口，不再增加呆板状态文案。

动效
从呼吸背景到单一的缓慢边框流动

呼吸与流动叠加会冲突，高频流动又显得焦躁。最终只保留 5.6 秒一周的双束边框光带，色值从刺眼纯白改为低饱和 Aqua，并支持减少动态效果。

视觉纪律
2px 圆角、8px 间距节奏、小型化控件

收敛过多圆角与大控件；重做下拉框；取消输入/选择控件的高亮边框，但仍保留可见的键盘焦点表现。浅色与深色模式跟随系统自动切换。

响应式
明确 540px 是产品模板的适配下限

曾验证 320px / 375px，随后根据实际使用场景改为只保证 540px 及以上；540px 下保持单列，539px 以下不再继续压缩布局。

抽屉行动区
固定底部操作，不让正文滚动遮挡

正文预留高度，行动按钮贴底；复核提示词不再占据页面。复制成功的 Toast 在抽屉水平与垂直居中，并明确引导用户回到对话窗口粘贴给 Agent。

数据细节
低风险隐藏建议后，列仍保持对齐

扫描卡片采用固定三列，建议为空时保留位置。力导向图长文本在 28 字符后省略，同时写入 title、SVG title 与 aria-label，兼顾悬停与辅助技术。

状态文案
“已确认”改为“Agent 核验完成 / 证据充分”

绿色传递流程完成与证据充分，而不是暗示 Skill 一定安全；风险等级继续独立显示。技术词“外部服务”也调整为“外部站点 / 数据平台 / 账号密钥”等更熟悉的表达。

一条没有被牺牲的无障碍底线

抽屉支持遮罩与 Esc 关闭、焦点约束与返回；Toast 使用状态播报；长图节点有完整文本；减少动态效果时动画停止。视觉上取消“输入框选中高亮边框”并不等于取消键盘焦点，二者被分别处理。

07

从“安全工具”到“Skill 守门人”：定位决定了如何被理解

产品传播没有把重点放在“发现了多少危险”，而是强调证据、复核与用户控制。验证标准也从“扫得快”转向“证据是否被完整理解”。

最终定位不是“替用户判断一切的安全裁判”，而是一个在使用前帮助用户看清权限、数据去向、费用与提示词影响的 Skill 守门人。Keeper 这个角色强调的是守住边界：它会提醒、解释、建议，但不会越过用户自动处置。

传播文案也围绕同一承诺展开：先看清，再安心使用。背景叙事强调 Skill 正在成为 Agent 扩展能力的重要入口；功能叙事则说明 Wizz Skill Keeper 会检查权限、外部站点、提示词操控、费用与冲突，并由 Agent 逐条复核证据。

POSITIONING

守门，而不是代替用户做决定

把能力定义为“审查、解释与提醒”，避免让安全产品本身成为新的高优先级指令源。

MESSAGE

先讲必要性，再讲检测能力

从文件、账号、外部站点与付费操作进入 Agent 工作流的变化讲起，让用户先理解为什么需要审查。

TONE

不靠恐惧推动使用

不把未知站点描述成危险，不把能力信号写成恶意事实；用明确证据和具体行动替代笼统警告。

LOCALIZATION

用户语言优先，中文默认

报告、建议与界面标签使用用户当前语言；无法判断时默认简体中文，产品描述提供中英双语版本。

验证策略本身也发生过转向

早期规模评测覆盖了 10 / 50 / 100 个 Skill：约 0.049s / 0.068s / 0.088s，峰值内存约 19.2 / 22.8 / 23.5 MiB，本地扫描不消耗模型 Token。黑盒质量最初只有 14/25 命中、2/3 安全对照误报；修复后达到 22/25 与 0/3，最终回归达到 25/25。

随后用户明确取消规模压测作为主要门槛，改用一个代表性真实样例做 one-shot 闭环：扫描器出候选，Agent 读 evidence.json 完成语义复核，review 命令生成正式报告和关系图。这个转向承认了一点：对本地脚本来说，速度不是最稀缺的能力，判断质量和可追溯性才是。

最后形成的产品观

Wizz Skill Keeper 的价值不在于“比人更快贴标签”，而在于把安全判断拆成可检查的责任链：本地工具负责尽量完整地收集事实，Agent 负责理解语境和影响，界面负责把结论讲得通俗但不过度，处置权仍留给用户。它最终守住的，不只是 Skill 的安全，也是用户对 Agent 结论的信任。
