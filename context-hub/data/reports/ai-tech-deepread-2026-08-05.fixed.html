Chapter 02

OpenAI：科学软件的瓶颈从实现转向验证

Scientific computing in the age of agentic AI · 2026-07-28

旧科学代码 安装脆弱 · 测试少 Codex / Claude Code 迁移 · 重构 · GPU 化 小步迭代 · 生成测试 边界条件仍需人判 可维护工具 上游合并 · 长期归属 验收目标、参考输出、统计行为、社区维护计划构成闭环 图意重绘：从旧科学软件到 Agent 辅助重构，再回到人类验证与长期维护。 OpenAI 这篇文章最重要的地方，不在于证明 coding agent 又能多快写代码，而在于它把科学软件的真实阻力拆出来了：科研领域并不缺一次性的脚本，缺的是可安装、可测试、可优化、有人长期负责的基础设施。文章汇总了八个 agent-assisted scientific computing 项目，主要发生在生命科学和数据密集型研究里，其中五个只用 Codex，三个结合 Codex 与 Claude Code。任务范围从包装系统现代化、遗留语言迁移、性能优化，到 GPU-native redesign。

第一层观点是，Agent 降低了工程劳动的价格，但没有取消科学判断。文章反复强调，研究者的角色正在从“亲手实现每一段代码”转向“定义要解决的问题、拆分阶段、设定验收标准、判断输出是否科学有效”。这是一个很实际的转移：如果没有外部参考、数值一致性、模拟数据真值、统计行为预期或既有工具 parity，Agent 很容易交出看似自信但实际错误的实现。这里的论据不是抽象宣言，而是来自多个 case 的共同模式：初版实现通常很快，最后一公里的边界条件、微小数值差异和可维护性反而最耗时。

第二层观点是，科学软件的“完成”不能只看新仓库能跑。OpenAI 特别指出，很多研究代码最初只是论文附属品，由小团队在有限时间里完成，缺少包装、测试、优化和长期支持。Agent 让重写、迁移和优化更便宜，但也可能制造新的碎片化：今天很漂亮的 rewrite，如果没有明确 owner、维护计划和上游协调，明天仍会变成无人维护的研究债务。文章里的 cyvcf2、MHCflurry 等例子说明，最理想的路径往往不是另起炉灶，而是尽量进入原项目治理结构；原项目废弃时，才需要新的社区归属。

第三层观点是，Agent 在科研里的价值不只是“帮忙写”，而是让以前不值得做的维护工作重新变得可行。科学软件维护长期处在尴尬位置：它直接影响发现速度和可复现性，却很难成为论文贡献。Agent 把这类低声望但高价值的劳动成本压低，使小团队能承担过去需要专职工程支持的工作。这里有一个明显的产品启发：面向科研的 AI 工具，不应把体验设计成“请我生成答案”，而应围绕 benchmark、reference output、run log、review queue、maintainer handoff 来设计。

Agent 补充论据： 如果把这篇文章迁移到企业软件语境，可以得到相同结论。老系统现代化的风险不在于能否把代码翻译成新框架，而在于谁定义兼容性、谁看异常流量、谁维护回滚窗口。Agent 的产能越高，越需要把验收和归属前置，否则只是更快地产生不可追责的改动。

Chapter 03

Google：自主研究系统必须原生生成证据链

Science One Framework · 2026-07-30

每个 claim 绑定证据 审计失败则改写，不硬撑 图意重绘：Science One 把证据链嵌入生成过程，再用 CoE Audit 做事后司法式复核。 Google Research 的 Science One Framework 把问题推进了一步：当 autonomous research agent 能够查文献、提假设、跑实验、写论文之后，真正危险的不是文本不像论文，而是它太像论文了。表面质量提高以后，引用不存在、方法和代码不一致、实验分数不可复现这些结构性问题更难被读者快速识别。文章提出 Chain-of-Evidence（CoE）和 CoE Audit，核心原则很直白：研究产物里的每个 claim 都要有证据链，且证据链必须真的支持这个 claim。

第一层观点是，证据链不能靠事后补链接。很多 AI research pipeline 先生成文本，再试图把事实和引用补齐；Google 的判断是，这种流程天然容易放大早期错误。Science One 反过来做：Problem Investigator 先通过学术 API 和 full-text PDF 建立文献 grounding；Discovery Engine 在隔离分支中并行探索、执行和评分；Paper Writer 在生成论文前，把事实 claim 做成结构化表示，并绑定到具体 workspace artifact。Claim Verifier 发现 claim 超出证据时，不是让模型继续圆，而是把表述改保守。

第二层观点是，研究 Agent 的评测也要从“结果好不好”改成“结果能不能被审”。CoE Audit 包含四类检查：报告分数能否独立 rerun 出来，代码是否违反任务规范，参考文献是否真实存在，方法描述是否忠于实际代码。文章给出的关键证据是，baseline 系统会出现最高 21% phantom references，并且常把简单确定性 heuristic 描述成复杂算法；Science One 在引用真实性、score verification 和 method-code alignment 上显著更好，同时没有牺牲求解表现，在多个 ADRS、MLE-Bench 和 Parameter Golf 类任务上保持竞争力。

第三层观点是，verifiability 是架构约束，不是合规装饰。Science One 的价值不只是“减少幻觉”，而是把幻觉从语言问题改写成 artifact integrity 问题：引用、日志、代码、分数、方法段之间必须可相互追溯。这对于下一代 AI scientist 很关键，因为科学共同体接受一个结果，并不是因为论文口吻专业，而是因为别人能沿着证据链复查。

这篇文章也有边界。它明确说 Science One 是实验原型，不是生产工具；CoE Audit 也不等于自动同行评审。一个 claim 即使证据链完整，也可能研究问题本身不重要，实验设计有偏，或者评价指标选错。这里反而说明人类科学判断没有被替代：Agent 可以把证据链整理得更硬，但“什么问题值得研究”“什么证据足够改变信念”仍然是人的工作。

Chapter 04

Anthropic：physical AI 的关键是把 Agent 嵌入受控生产流程

UST is bringing Claude to physical AI · 2026-07-09

早发现缺陷 · 缩短验证周期 · 保留审批和数据控制 图意重绘：Claude 不是脱离产线行动，而是嵌入验证、数字孪生、人审和审计控制。 Anthropic 这篇不是论文，而是一个应用案例，但它对 AI 工程化很有价值，因为它把 Agent 放进了最不适合“随便试试”的场景：半导体、汽车、制造、通信、嵌入式、IoT 等生产流程。文章中的 physical AI 指的是进入设备和工程流程的智能，而不是单纯的机器人演示。UST 的角色也关键：它不是把 Claude 当聊天工具卖给客户，而是把 Claude 放进自己已经为客户运行的工程环境、验证平台和行业流程里。

第一层观点是，physical AI 的真实入口往往不是“机器人自己行动”，而是设计验证和故障发现。文章最清晰的例子是 UST 的 iDEC 平台：硬件和硅片量产前需要验证设计是否按预期工作，传统流程里工程师手写 test scripts、运行、读结果、再改。UST 说它的闭环管线已经能把硬件设计读入、生成并运行 regression tests、把实时设备数据和 digital twin 对比，并将验证周期缩短 50% 到 70%，把常见四天周转压到 48 小时。Claude Code 被接入为 reasoning layer，读取 pinouts 和 schematics，编写并运行回归测试，识别 firmware regressions 和 signal-integrity faults。

第二层观点是，高风险行业里 Agent 的产品形态必须是“无新工具学习成本 + 人类审批 + 审计控制”。文章提到 healthcare、telecom、banking 三个扩展平台：CarePath 把分散健康数据整理成 care team 的下一步建议，但推荐动作进入 member 前有人批准；IntelliOps 帮运营团队识别服务问题、预测无线接入网故障、缩短 outage response，但仍经过人类 approval；FinX 把 agents 嵌入银行 workflow，支持 case handling、servicing automation、knowledge retrieval 和 decision support。它们的共同点不是全自动，而是让 Agent 出现在已有责任链中。

第三层观点是，physical AI 的部署可信度来自组织能力，而不只是模型能力。UST 计划培训 20,000 名 associates，并建设专门部署团队；Anthropic 提供 enablement、technical guidance 和 certification。这说明一个生产级 Agent 系统至少需要三层工程：模型和工具接口，行业 workflow 和数据控制，组织培训和审计制度。缺任何一层，都会从“工程提效”滑向“不可控自动化”。

这篇案例的证据量适中，但不是学术评测，所以需要谨慎读。它给出了 iDEC cycle time 的改进数字、明确的流程位置和多个行业落点；但没有公开对照实验、误报漏报率、审批通过率或事故复盘。因此更合理的结论不是“Claude 已经证明能控制 physical AI”，而是“Claude 正被包装成受控生产流程里的推理与测试层”。

Chapter 05

交叉总结：Agent 的新护城河是“外部证据”

三篇文章的共同问题，是如何让 AI 进入真实工作而不变成不可审计的黑箱。

OpenAI 讲科学软件维护，Google 讲自主研究论文，Anthropic 讲 physical AI 生产流程。三篇文章表面跨度很大，底层却是同一个结构：Agent 只有接上外部证据，才有资格进入长期工作。科学软件里的外部证据是测试、参考输出、性能 benchmark、上游 maintainer；Science One 里的外部证据是文献 API、代码、日志、独立 rerun、claim verifier；UST 案例里的外部证据是 schematics、pinouts、regression tests、digital twin、human approval 和 audit controls。

这意味着 AI 产品的主战场正在从“模型怎么想”转到“系统怎么证明”。过去我们常把 prompt、context window、model choice 当作核心设计变量；现在更重要的是 artifact schema、evidence graph、run log、approval gate、ownership record。Agent 越会行动，越要把行动拆成可验证中间物；Agent 越能写出完整叙述，越要把叙述绑定到证据链；Agent 越能进入物理和金融流程，越要让它待在已有控制面里。

三篇文章也共同提醒一个反直觉点：人类没有被挤到流程外，而是被挪到更前、更硬的位置。人不必手写每个测试、不必逐字起草每段论文、不必亲自翻完每条告警；但人必须定义验收目标、判断证据是否足够、决定何时合并、何时发布、何时交付客户。未来的高价值 AI 工程不是把人从系统里拿掉，而是把人的判断做成系统结构。

因此，一个好的 Agent 产品可以用四个问题审查：第一，它的每个结论能否追溯到具体证据；第二，它的每个动作是否有外部验收标准；第三，它失败时是否能被定位到 artifact、日志或权限边界；第四，它生成的新资产是否有长期 owner。答不出来，就算模型能力再强，也还只是演示。
